# Conventions

1. **App id.** Every tool has one id, used in `tools.json`, the folder name `tools/<id>/`, the database prefix and the `data-app` attribute. Non-tool pages use `hub` (index) and `login`.
2. **Database naming.** All tables, functions, policies and constraints are `snake_case` and start with the app id: `<id>_<thing>`. Shared infrastructure starts with `hub_`. Examples: `wachter_items`, `expenses_entries`, `hub_app_access`.
   - Policies: `<table>_<purpose>`. Unique constraints: `<table>_<columns>_key`.
   - Text shown to users has a language suffix: `label_en`, later `label_zh`.
   - Small lookup lists (categories, currencies) are tables with a text key, `label_en` and `sort_order`.
3. **Access is per app, and is data.** Table `hub_app_access (user_id, app_id)` says who may use which app. Row-level security on every app table calls `public.hub_has_access('<id>')`. Never put user ids in policies.
4. **Row-level security is mandatory** on every table. Only the publishable Supabase key ships in the browser.
5. **CSS uses variables only.** No hex, `rgb()` or `rgba()` outside the token blocks: the `:root` block in `base.css` (shared tokens) and the `:root[data-app="..."]` blocks in `theme.css` (tokens only one app uses, such as the expense `--cat-*` colors). For translucent colors use `color-mix(in srgb, var(--token) N%, transparent)`.
6. **Load order on every page:** `base.css`, then `theme.css`, then the app's own `style.css`.
7. **Every page sets `<html data-app="<id>">`.** This lets `theme.css` restyle one app: `:root[data-app="expenses"] { --accent: ...; }`.
8. **Shared UI pieces live in `base.css`.** An app's own stylesheet holds only what is specific to that app. When a second app needs a rule, move it to `base.css` then, not before.
   - Stylesheet links carry `?v=N`. When `base.css` or `theme.css` changes, give both the same new number on every page (hub, login and all apps). When an app's `style.css` changes, bump that app's own number. This stops a browser from mixing a cached file with a new one.
9. **Icons** are single SVG files with no hex colors. Strokes use classes `c1` (accent) and `c2` (accent-2). The hub inlines them so they follow the theme.
10. **User-supplied text** is inserted with `textContent`, never `innerHTML`. The one exception is Wachter's entry bodies, which are stored as HTML: they are shown only through `tools/wachter/sanitize.js`, which keeps a fixed list of tags and drops everything else.
11. **Shared code lives in `shared/`.** `shared/dates.js` has the local-date helpers; `shared/i18n.js` has the language machinery. Do not copy either into an app.
12. **Language.** The language is chosen only in the hub's settings and saved per device (`localStorage` key `hub.lang`); every app and the login page just read it, so apps have no language control and nothing to re-render on a change (the page is loaded fresh in the chosen language). UI text lives in code: each app's `i18n.js` holds its own strings and builds its translator with `createI18n({ strings })`; words every app needs (Home, Save, Close, ...) are in `shared/i18n.js` and an app string with the same key overrides them. Text that comes from the database has `_en` / `_zh` columns and is shown with `nameOf` / `labelOf`, never translated in code.
13. **Install and push.** The hub is the one installable app: `manifest.webmanifest` and `sw.js` sit at the site root, and the service worker covers every tool, so a tool needs no install or push code of its own. Only the hub and login pages carry the manifest and `apple-touch-icon` tags. Notifications are switched on in the hub's settings (`push.js`) and sent by a Supabase function as `{ title, body, url }`, where `url` is relative to the hub root (e.g. `tools/expenses/`). Home-screen icons are PNGs in `icons/` because iOS cannot use SVG there (an exception to rule 9).
